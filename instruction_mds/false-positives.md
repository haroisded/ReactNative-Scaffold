# Known false positives

Tool findings that are wrong **in this repo**. Read a section only when its tool has just spoken.

Most suppressions live in tool config, not here: `.fallowignore`, `.oxlintrc.json` overrides and the
`--gate` flags. This file is the short register of what config cannot express.

## Rules

1. **Check this register before reacting to a tool finding.** A listed finding costs one line in the
   pass record and no investigation.
2. **Never run `fallow fix` in this repo.** Not the command, not `--fix`, not an editor quick-fix on
   its output. Every registered dependency finding is `auto_fixable: true`; the fixer cannot tell
   them from real ones and will strip `react-native-reanimated`, `react-native-web` and
   `react-native-gesture-handler` out of `package.json` and report success. Fix by hand.
3. **A finding not listed here is not automatically false.** Establish each with evidence — a
   dependent in `node_modules`, a reference in `app.json` or `tools/`, or a rule in `instruction_mds/`.
4. **Cannot establish it? Leave it.** Do not delete, suppress or tidy it away. Record it and surface
   it to the human.
5. **Established a new one? Add it here in the same pass**, with its evidence, or add the suppression
   to the tool's own config and note which file carries it.
6. **Where a tool and this repo's docs disagree, the docs win.** The tool cannot see the reasoning.
7. **Never quote a headline score.** `fallow health` grades this repo D, and half the penalty is the
   dependency findings below. Cite the underlying findings.
8. **Findings inside generated or vendored code are not ours to fix** — but whether that code stays
   *is* ours. Two different decisions (§2).

## 1. Unused dependencies

An Expo app wires most packages through native autolinking, `app.json` config plugins and peer
relationships, none of which are `import` statements, and fallow's graph is built from imports.

**Leave every one of these in `package.json`:**

| Package | Why the tool cannot see it |
| --- | --- |
| `expo-build-properties` | `app.json` → `plugins`; fallow does not read `app.json` |
| `expo-image` | `app.json` → `plugins`; also the image component every grid uses |
| `expo-glass-effect` | `expo-router` depends on it |
| `expo-symbols` | `expo-router` depends on it |
| `react-native-gesture-handler` | required by `expo-router`, `react-native-screens`, `react-native-drawer-layout` |
| `react-native-reanimated` | required by the same three |
| `react-native-worklets` | required by `expo-modules-core`, `react-native-reanimated`, `react-native-gesture-handler` |
| `react-native-web` | Kept on purpose, not required. This app has no web target (README, *What ships*), and nothing under `src/` imports it, so it never enters the native bundle. `expo`, `expo-router`, `expo-image` and `expo-system-ui` declare it as an **optional** peer; `babel-preset-expo` does not depend on it at all, which an earlier version of this row got wrong. Removing it buys node_modules size and risks Metro resolution — not a trade worth making |
| `react-dom` | Same call. Its only non-optional dependent is `react-native-web`'s peer range; nothing here imports it |
| `react-native-vector-icons` | Paper imports it internally |
| `expo-dev-client` | the development build itself |
| `expo-atlas` (dev) | `tools/atlas.mjs` spawns it; `tools/` is outside the analysed graph |
| `@expo/ui` | Kept on purpose, not imported yet (the human's call, 2026-10-08). [`frontend.md`](./frontend.md)'s Date / time field row uses its `DateTimePicker`, and it is a native module: removing it now costs one dev-build rebuild to drop it and another to re-add it with the rebuild's first date field. Delete this row and its `REGISTERED_DEPS` entry once a date field imports it |

**Unverified — do not delete, do not suppress, do not classify.** No importer and no dependent found
for `expo-device` and `expo-system-ui`. Listed so nobody re-investigates them by accident, not
because they are cleared. `expo-system-ui` probably serves `app.json`'s
`userInterfaceStyle: "automatic"`, but that is inference, not evidence.

`expo-status-bar` was on that list until 2026-09-19, when `src/app/_layout.tsx` started rendering
`<StatusBar>` to keep the status-bar icons legible under a hand-picked theme. It is a real import
now, so it is off the list and out of `tools/fallow-verdict.mjs` — a registration nothing needs is
the kind of table that starts lying.

## 2. Generated and vendored code

| Path | What it is | Verdict |
| --- | --- | --- |
| `src/lib/database.types.ts` | Generated by `supabase gen types typescript --linked` | Duplication and unused-type findings are noise — the next migration regenerates it wholesale. Never hand-edit. Excluded from fallow in `.fallowrc.json` (§3) |
| `tools/oxlint/anti-slop/**` | Vendored by the `install-anti-slop` skill | A third-party lint plugin, not application code, not in the app bundle. Duplication findings inside it are noise |
| `tools/*.mjs` | npm-script entry points — `atlas`, `build:migrations`, `check:migrations`, and `fallow-verdict.mjs`, which fallow runs on itself | `unused_files` on any of them is the graph being built from imports. Nothing imports a script you invoke from `package.json`. Confirm against `scripts` before dismissing one |

*"It is vendored"* answers a duplication or complexity finding. It does **not** answer *"nothing
imports this file"* — vendored code with zero importers and no entry in `.oxlintrc.json` is genuinely
dead and correct to delete.

## 3. fallow specifics

- **`fallow recommend`'s `entry` proposal is wrong here.** It offers `src/index.{ts,tsx,js,jsx}` and
  `src/main.{ts,tsx,js,jsx}`; neither exists. Routing is file-based through expo-router. No `entry`
  is the supported state and `fallow doctor` reports `Status: ready` in it.
- **`.fallowrc.json` sets exactly two things, and each replaces a finding nothing could fix.**
  `ignorePatterns` drops `src/lib/database.types.ts` (§2: generated, its duplication and unused
  types are noise). `complexity-crap: off` drops the CRAP score, which multiplies complexity by the
  share of a function no test covers: with no test runner in this repo every function is 0% covered,
  so any function with five branches fails, and splitting it only makes two that fail. The cyclomatic
  (20) and cognitive (15) limits stay on and still fail the verdict. Rejected: adding `jest-expo` to
  earn coverage — a test runner and a suite for a scaffold whose device behaviour is proven by
  acceptance tests (`testing-workflow.md`). Turn CRAP back on the day a test runner lands.
- **`npx fallow review` does not run on this machine** — `Error: could not create a temporary
  worktree for base ref '<sha>'`. Pass `--gate all` to skip the base-snapshot pass. The cost is that
  every finding in a changed file is reported, inherited ones included, so scope the output to the
  current diff yourself. `tools/fallow-verdict.mjs` already passes it — run that, never fallow
  directly ([`token-budget.md`](./token-budget.md) §1).
- **Under `--gate all` the verdict is `fail` on the §1 dependencies alone.** The script says so
  (`the fail is registered findings only`) — that line means nothing to fix.
- **`workspace_diagnostics`** (`boundaries-not-configured`, `rule-packs-not-configured`) are notes
  that a detector did not run, not findings. The script prints them as `not run:`.

## 4. oxlint and npm

- **`MODULE_TYPELESS_PACKAGE_JSON` on `npm run lint`** came from `tools/oxlint/anti-slop/index.ts`
  being TypeScript in a package with no `"type": "module"`. `package.json` has carried
  `"type": "module"` since 2026-10-01 (the human's request), and the warning is gone. Checked that
  day with it set: lint, typecheck, `npx expo config` (`app.config.ts` still loads), the `tools/*.mjs`
  scripts, and `npx expo export --platform android` (Metro bundles every module). Not yet checked: an
  iOS export, and a run on a device. This entry used to call the field harmful because it changes
  module resolution for the whole app; no tracked `.js` file uses `require` or `module.exports`, so
  nothing broke. If the warning comes back, oxlint still exits 0 — check the exit code, not the
  text; PowerShell renders the stderr as a `NativeCommandError`.
- **Colour literals in `src/themes.js` are correct.** `.oxlintrc.json` turns
  `anti-slop/no-design-literals` on for `src/**` and off for `src/themes.js`.

## 5. Supabase

- **`20260902000003_rls_auto_enable.sql` reports Success while installing nothing.** Treat a green
  result as meaning nothing and write `enable row level security` by hand
  ([`migrations.md` §5](./migrations.md)).
- **`supabase db lint` is not an RLS check.** It type-checks plpgsql. The dashboard's Security
  Advisor (`rls_disabled_in_public`) answers whether a table is protected.

## 6. Documented exceptions a reviewer may flag

Each is a deliberate decision, not a defect:

| If flagged | Why it stays |
| --- | --- |
| Two separate `AppState` listeners — `supabase.ts` and `query.ts` | Different jobs: token refresh start/stop, and reporting foreground to React Query |
| `.throwOnError()` on every Supabase call | Load-bearing — without it the thrown error is a plain object, not a `PostgrestError`: no stack, no class to test a code against ([`data-layer.md` §2](./data-layer.md)) |
| `key={columns}` on a `FlashList` | Insurance; it only changes on a column-boundary crossing, already a full relayout |
| `profiles` is not `force row level security` | Forcing it subjects the owner to the policies, and the signup trigger inserts as the owner with no JWT |
| Missing `persistSession`, `autoRefreshToken`, `detectSessionInUrl`, `lock` | All four are already default, `@deprecated`, or inert here |
| No barrel files / `index.ts` re-exports | [`structure.md` §7](./structure.md) |
| `Avatar.Text label=""` instead of a sized `View` | A radius number at a call site is forbidden; `Avatar` is round through Paper's own stylesheet |

## 7. Skill contradictions

Where a skill contradicts a rule in `instruction_mds/`, the doc wins and the finding is registered, not fixed.
The standing cases live with the rule they contradict, not here:

- Frontend, styling, type and layout → [`frontend.md` §8](./frontend.md)
- Expo, structure and data → [`expo.md` §3](./expo.md)

A new contradiction gets a row in the relevant file in the same pass — never a quiet change to the
code.

## 8. Adding an entry

Four things, or it does not go in:

- **The finding**, as the tool words it.
- **The tool**, and the command that produced it.
- **The evidence** that settles it — a dependent, a config reference, a file path, a documented rule.
  Not a plausible story.
- **The verdict**: confirmed false positive, or unverified. Those are the only two.

Prefer a **class** over a row where one exists (§2 retires a dozen findings in two rows). Re-check §1
against the tool whenever a dependency is added or removed — and keep `REGISTERED_DEPS` in
`tools/fallow-verdict.mjs` equal to §1's two lists, or a registered dependency shows up as a finding:

```bash
node tools/fallow-verdict.mjs 50
```

Write from output, never from prediction. An unverified entry is allowed to stay unverified.
